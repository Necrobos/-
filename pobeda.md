## 1. Алгебра и геометрия. Линейная зависимость векторов

**Условие.** При каких `a` система `x=(1,a,3), y=(2,5,a+5), z=(3,7,10)` в `R³` линейно зависима?

**Теория.** Три вектора в `R³` линейно зависимы ⟺ определитель матрицы, составленной из их координат, равен нулю (векторы лежат в одной плоскости / один выражается через другие).

**Решение.**
```
| 1   a    3  |
| 2   5   a+5 |
| 3   7   10  |
```
Раскрываем по первой строке:
`det = 1·(5·10 − (a+5)·7) − a·(2·10 − (a+5)·3) + 3·(2·7 − 5·3)`
`= 1·(50 − 7a − 35) − a·(20 − 3a − 15) + 3·(14 − 15)`
`= (15 − 7a) − a(5 − 3a) − 3`
`= 15 − 7a − 5a + 3a² − 3 = 3a² − 12a + 12`

Приравниваем к нулю: `3a² − 12a + 12 = 0 ⟹ a² − 4a + 4 = 0 ⟹ (a−2)² = 0 ⟹ a = 2`.

**Ответ: a = 2** (единственное значение, корень кратности 2).

## 2. Теория вероятностей. Ровно одно успешное бурение

**Условие.** `P(X)=0.5, P(Y)=0.4, P(Z)=0.1`, события независимы. Найти вероятность того, что успешным окажется **ровно одно** бурение.

**Теория.** Для независимых событий вероятность того, что произойдёт ровно одно из трёх, — это сумма вероятностей трёх непересекающихся исходов («успех только в X», «только в Y», «только в Z»):
`P = p_X q_Y q_Z + q_X p_Y q_Z + q_X q_Y p_Z`, где `q=1-p`.

**Решение.** `q_X=0.5, q_Y=0.6, q_Z=0.9`.
- успех только в X: `0.5·0.6·0.9 = 0.27`
- успех только в Y: `0.5·0.4·0.9 = 0.18`
- успех только в Z: `0.5·0.6·0.1 = 0.03`

`P = 0.27+0.18+0.03 = 0.48`.

**Ответ: 0,48.**

## 3. Математический анализ. Прямоугольник максимальной площади при фиксированном периметре

**Условие.** Проволока длины `L` согнута в прямоугольник. Найти размеры прямоугольника с наибольшей площадью.

**Решение.** Пусть стороны `x` и `y`, периметр `2x+2y=L ⟹ y=L/2−x`, `0<x<L/2`.
Площадь `S(x)=x(L/2−x)=Lx/2 − x²`.
`S'(x) = L/2 − 2x`. Приравниваем к нулю: `x=L/4`, тогда `y=L/2−L/4=L/4`.
`S''(x)=-2<0` — это максимум.

Оба измерения равны `L/4` — оптимальный прямоугольник является **квадратом** со стороной `L/4`, максимальная площадь `S_max = L²/16`.

**Ответ: квадрат со стороной L/4 (площадь L²/16).**

## 4. Базы данных: `LEFT JOIN` и `FULL JOIN` со сложным условием

**Данные:**
```
DETAILS:    (1,Detail1,100) (2,Detail2,50) (3,Detail3,100) (4,Detail4,NULL)
PARAMETERS: (1,P1,100) (2,P2,50) (3,P3,50) (4,P4,NULL) (5,P5,NULL)
```

### A. `LEFT JOIN ... ON DETAILS.SIZE = PARAMETERS.SIZE`

**Доп. теория.** В SQL `NULL = NULL` возвращает **UNKNOWN** (а не TRUE) — по правилам трёхзначной логики (TRUE/FALSE/UNKNOWN). Поэтому строка с `SIZE = NULL` никогда не совпадёт ни с одной строкой правой таблицы, даже если у той тоже `SIZE = NULL`. При `LEFT JOIN` такая непарная строка левой таблицы всё равно попадает в результат, но с `NULL` вместо значений правой таблицы.

**Разбор соответствий по SIZE:**
- `Detail1` (100) ⟷ `PARAMETERS.SIZE=100` → только `P1` (1 строка)
- `Detail2` (50) ⟷ `PARAMETERS.SIZE=50` → `P2`, `P3` (2 строки)
- `Detail3` (100) ⟷ `P1` (1 строка)
- `Detail4` (NULL) ⟷ ничего не совпадает (NULL≠NULL) → LEFT JOIN сохраняет строку с `PARAMETERS.NAME = NULL`

**Итого 5 строк**, после `ORDER BY 1,2`:
```
Detail1  P1
Detail2  P2
Detail2  P3
Detail3  P1
Detail4  NULL
```

### B. `FULL JOIN ... ON DETAILS.SIZE = PARAMETERS.SIZE OR DETAILS.SIZE IS NULL`

**Доп. теория.** Условие соединения — это **дизъюнкция** двух предикатов. Второй предикат `DETAILS.SIZE IS NULL` не зависит от `PARAMETERS` вообще — если он истинен, то условие ON истинно **для любой** строки правой таблицы. Значит строка `DETAILS`, у которой `SIZE=NULL`, автоматически образует пару **со всеми** строками `PARAMETERS` (полное соединение по этой строке).

**Разбор:**
- `Detail1` (100): матч только по равенству → `P1` (1 строка)
- `Detail2` (50): → `P2`, `P3` (2 строки)
- `Detail3` (100): → `P1` (1 строка)
- `Detail4` (NULL): условие `DETAILS.SIZE IS NULL` истинно для **каждой** строки PARAMETERS → пары со всеми пятью: `P1,P2,P3,P4,P5` (5 строк)

Всего сопоставлено `1+2+1+5=9` пар. Проверяем, остались ли непарные строки (для полноты `FULL JOIN`): все строки `DETAILS` нашли пару, все строки `PARAMETERS` (включая `P4`, `P5`) нашли пару через `Detail4` — значит непарных строк с обеих сторон нет, и `FULL JOIN` фактически выродился в результат, эквивалентный `INNER JOIN` по этому условию.

**Итого 9 строк**, после `ORDER BY 1,2`:
```
Detail1  P1
Detail2  P2
Detail2  P3
Detail3  P1
Detail4  P1
Detail4  P2
Detail4  P3
Detail4  P4
Detail4  P5
```

## 5. C#: порядок инициализации, конструкторы, цепочки `this(...)`/неявный `base()`

**Доп. теория (важно для этой задачи).**
1. Если конструктор производного класса **не содержит** явного `: base(...)`, компилятор **всегда** неявно подставляет вызов **беспараметрического** конструктора базового класса `base()`. Наличие в базовом классе перегруженного конструктора с параметрами `Class(int i)` ничего не меняет — он вызывается **только** при явном `: base(i)`.
2. Порядок инициализации объекта: (а) выполняются инициализаторы полей базового класса → (б) выполняется тело конструктора базового класса → (в) выполняются инициализаторы полей производного класса → (г) выполняется тело конструктора производного класса. При цепочке `: this(...)` пункты (а)-(в) выполняются **один раз** — при входе в тот конструктор цепочки, который (прямо или через `this`) содержит неявный/явный вызов `base(...)`, а затем управление возвращается по цепочке `this` к «внешнему» конструктору.
3. Если параметр конструктора имеет то же имя, что и поле (`public Class(int i) { i = 3; ... }`), то внутри тела `i` без `this.` — это **параметр**, а не поле: присваивание `i=3` меняет только локальный параметр, поле класса не затрагивается. В данной задаче это не сработало на практике, так как `Class(int i)` вообще ни разу не вызывается — используется только `Class()`.

**Пошаговый разбор кода:**

```csharp
ClassB B = new ClassB(50);
```
`ClassB(int a)` не содержит `: this(...)` или `: base(...)` → неявно вызывается `base()` = `Class()`:
- поле `i` инициализируется в 100, затем тело `Class()`: `i=2; Write("A2")` → печать **`A2`**, поле `i=2`.
- возврат в `ClassB`: инициализатор поля `j=400`, затем тело `ClassB(int a)`: `j=6; WriteLine("B6")` → печать **`B6`** + перевод строки.

Вывод от этой строки: `A2B6\n`

```csharp
B = new ClassB(25, 35);
```
`ClassB(int a, int b) : this(a)` — сначала полностью выполняется `ClassB(int a=25)`:
- `ClassB(25)` не содержит `this`/`base` → неявный `base()` = `Class()`: `i=100→2`, печать `A2`.
- поле `j=400`, тело `ClassB(int a)`: `j=6`, `WriteLine("B6")` → печать `B6\n`.

Возврат в тело `ClassB(25,35)`: `j = b = 35; WriteLine("B7")` → печать `B7\n`.

Вывод от этой строки: `A2B6\nB7\n`

```csharp
B.Show();  // Console.Write(i + " " + j)
```
Текущий объект — созданный `new ClassB(25,35)`, у него `i=2` (установлено в `Class()`, `Class(int i)` вообще не вызывался), `j=35` (установлено в теле `ClassB(int a,int b)`).
Печать: **`2 35`** (без перевода строки).

**Итоговый вывод на экране:**
```
A2B6
A2B6
B7
2 35
```

## 6. Java: коллекции, `HashMap`, `equals`/`hashCode`

### A. Сложность поиска по ключу в `HashMap`
**Доп. теория.** `HashMap` — хеш-таблица: ключ преобразуется в индекс корзины (bucket) через `hashCode()`, что при равномерном распределении и малом числе коллизий даёт доступ **за O(1) в среднем** (амортизированная константа). В худшем случае (много коллизий в одной корзине, до Java 8 — цепочка списком) сложность деградирует до O(n), но именно **средняя** оценка — O(1).

**Ответ: 3) O(1).**

### B. Интерфейс `Set`
**Доп. теория.** `Set<E>` наследует `Collection<E>` и добавляет контракт: **не допускает дублирующихся элементов** (используя `equals()`/`hashCode()` для проверки уникальности). Доступ по индексу отсутствует (это свойство `List`), реализации `Comparable` требует не `Set` вообще, а конкретно `SortedSet`/`TreeSet`; «словарь ключ-значение» — это `Map`, а не `Set`.

**Ответ: 1) наследуется коллекциями, которые не могут содержать дубликатов.**

### C. Поведение `HashMap` при мутации ключа после вставки

**Доп. теория — критически важный момент.** Контракт `hashCode()`/`equals()` в Java требует: если объект используется как ключ изменяемого (mutable) типа в `HashMap`, и поля, участвующие в вычислении `hashCode()`, **изменяются после вставки в map**, то повторный поиск этого объекта может завершиться неудачей. Причина: при `put()` бакет (индекс корзины) вычисляется на основе `hashCode()` **в момент вставки** (когда `age=42`), а при `get()` `HashMap` заново вычисляет `hashCode()` от **текущего** состояния объекта (`age=41` после мутации) и ищет уже в **другом** бакете, где записи фактически нет — либо, даже попав в тот же бакет, использует `equals()`, который тоже теперь даёт другой результат сравнения.

В коде: `user1 = User("user1",42)`, `user2 = User("user1",43)`. Так как `age` отличается — `equals()` и `hashCode()` для `user1` и `user2` различны ⟹ это **два разных ключа**, обе записи благополучно попадают в map (`put` не перезаписывает друг друга).
Далее `user1.age = 41` — меняется поле, входящее в `hashCode()`, уже **после** размещения `user1` в map. Хеш-код объекта, находящегося в конкретном бакете, «застрял» на старом значении бакета (вычисленного при `age=42`), а `get(user1)` пересчитывает хеш заново с `age=41` — почти наверняка попадает в **другой** бакет, где искомой записи нет.

**Ответ: `null`** (программа не находит запись — классическая демонстрация антипаттерна «мутация полей, участвующих в hashCode, после использования объекта как ключа коллекции»).

### D. `List` vs `Set`

| | List | Set |
|---|---|---|
| Дубликаты | допускаются | **не** допускаются |
| Порядок | сохраняется порядок добавления, есть индекс | не гарантирован (кроме `LinkedHashSet`/`TreeSet`) |
| Доступ | по индексу (`get(i)`), `O(1)` для `ArrayList` | только через итератор/`contains()` |
| Типичные реализации | `ArrayList`, `LinkedList` | `HashSet`, `LinkedHashSet`, `TreeSet` |

## 7. Разбор блоков кода на разных языках

### A. Python 3
```python
x, y = 1, 2; z = x if x else y
print(z)
```
**Теория.** Тернарное выражение `A if cond else B` в Python вычисляет `cond` как булево значение: `x=1` — истинно (любое ненулевое число truthy), значит `z = x = 1`.

**Ответ: 1.**

### B. C++ (указатель и префиксный инкремент)
```cpp
int* x = new int[2];
x[0] = 10; x[1] = 20;
cout << *++x << ", " << *x;
```
**Доп. теория.** `++x` — префиксный инкремент **указателя**: `x` смещается на размер `int` вперёд (теперь указывает на `x[1]`), и это новое значение указателя сразу используется в том же выражении. `*++x` — разыменование уже сдвинутого указателя → значение `x[1] = 20`. Так как инкремент **изменяет саму переменную-указатель** (а не временную копию), при повторном использовании `*x` далее в выражении указатель уже необратимо смещён — второе разыменование тоже даёт `20`.

**Ответ: `20, 20`.**
*(Если исходный код подразумевал иную запись правой части — принцип решения тот же: сначала разобраться, куда фактически указывает `x` после каждой операции над самим указателем, а не только «что лежало по старому адресу».)*

### C. C#: `using`-блок и `IDisposable`
```csharp
class X : IDisposable { public void Dispose(){} }
...
int b = 0;
using (X a = new X()) { b = 100; }
Console.WriteLine("{0}", b);
```
**Доп. теория.** Конструкция `using (...)` — это синтаксический сахар над `try { ... } finally { a.Dispose(); }`: она гарантирует вызов `Dispose()` при выходе из блока (даже при исключении), но **не влияет** на переменные вне области действия `using`, кроме уничтожения самого disposable-объекта `a`. Переменная `b` объявлена снаружи и просто получает присваивание `100` внутри блока — `Dispose()` в данном классе пустой и никак не меняет `b`.

**Ответ: `100`.**

## 8. Паттерны, отделяющие логику создания объекта от клиента

**Доп. теория.** По классификации GoF паттерны делятся на порождающие (creational), структурные (structural) и поведенческие (behavioral). Именно **порождающие** паттерны инкапсулируют логику создания объектов, скрывая от клиента конкретный класс создаваемого экземпляра:
- **Итератор** — поведенческий паттерн (унифицированный последовательный доступ к элементам коллекции), к созданию объектов отношения не имеет. ✘
- **Статическая фабрика** (static factory method) — создание объекта через статический метод вместо публичного конструктора, клиент не знает деталей создания и может получать разные подклассы через единый метод. ✔
- **Прототип** (prototype) — создание новых объектов путём клонирования существующего экземпляра, а не через `new`; клиент не завязан на конкретный конструктор класса. ✔
- **Абстрактная фабрика** — интерфейс для создания семейств взаимосвязанных объектов без указания их конкретных классов. ✔

**Ответ: 2) статическая фабрика, 3) прототип, 4) абстрактная фабрика.**

## 9. SOLID: рефакторинг иерархии наследования

**Условие (по схеме).** Было: `Class1 → Class2 → Class3` (линейная цепочка наследования: `Class3` наследует `Class2`, `Class2` наследует `Class1`). Стало: `Class2` и `Class3` — оба **напрямую** наследуют `Class1` (то есть иерархия «расплющена»: `Class1 ← Class2`, `Class1 ← Class3`, но `Class3` больше не наследует `Class2`).

**Доп. теория.** **Принцип подстановки Лисков (Liskov Substitution Principle, LSP)** гласит: объекты производного класса должны быть взаимозаменяемы с объектами базового класса без нарушения корректности программы. Частая причина нарушения LSP — «глубокая» цепочка наследования, где промежуточный класс (`Class2`) добавляет поведение или ограничения, из-за которых конечный класс (`Class3`) перестаёт быть корректной заменой `Class2` в контексте, ожидающем именно `Class2` (классический пример — «Квадрат не является Прямоугольником» при наследовании `Square : Rectangle`). Разрыв цепочки `Class3→Class2→Class1` на две независимые ветви `Class2→Class1` и `Class3→Class1` устраняет ложную иерархию «is-a», которая нарушала подстановочность, — то есть напрямую восстанавливает соблюдение **LSP**.

*(SRP — принцип единственной ответственности — касается количества причин для изменения класса, а не структуры наследования; к данной схеме отношения не имеет.)*

**Ответ: 1) LSP.**
